Play, export, snapshots

This page covers how a module leaves the editor: play-testing it, reading why a play-test did not start, sharing it as a pack, going back to an earlier version, and building it into a game people can install.

You'll learnwhat Play does and where its logs are, how export and import work, how snapshots are kept and restored, what Settings controls, and how the Packager makes an app Time20 minutes Needsa module with a map; the app for Play (Getting started)

Play

▶ Play is at the foot of the rail, on Home as ▶ play from map, in the map editor's toolbar, and on each map's row in 🗺 Maps. Where the game starts depends on which you press:

  • Play in the map editor, or on the rail, starts on the map you are editing (marked ✎ in the Maps list). A module reopens on the map you edited last on this device, so the rail's Play plays that one.
  • ▶ on a map's row in 🗺 Maps starts on that map, whichever one you are editing.
  • Play on Home starts on the module's starting map, and its label names it. Set it in ⚙ Settings → starting map. Left at the first by name, it is the first map in alphabetical order, which is also where the game starts for a player.

In order, Play:

  1. bakes every stale source (a texture, sprite or track changed since its last bake; see Plugins);
  2. writes the module into the game's files on the device;
  3. launches the game on that map. The server starts every other map of the module too, so a graph's change_map finds the map it names.

If the module does not bake, nothing is launched. Play also refuses to start while a graph has problems.

The progress panel

From the moment you press Play until the game appears, a full-screen panel shows what is happening, titled Play: module · map. It has a bar and these steps, each ticked with the time it took:

  1. baking sources
  2. checking maps and graphs
  3. baking maps
  4. writing the module
  5. starting the game

If a step fails, the panel stays on screen: the step is marked ✗, the line under the bar says "step failed", and the error is shown. Two buttons take you on: play log opens the Play log (below), and back to the studio closes the panel.

Coming back

The game's ◀ Studio link returns you to the map you were testing, with the view as you left it. On Android, the phone's Back does the same. The studio remembers where you were for an hour; after that it opens on Home as usual.

The Play log

On a phone there is no console, so a play-test that does not start says why in the studio. Each Play starts three log files afresh, in the game's logs/ folder:

FileWhat is in it
play-studio.logthe studio's side: the map, module.txt, the scripts the map declares, what the bake warned about, and the launch's own answer
play-server.logevery line the game server says
play-game.logthe game page's console, uncaught errors included

The Play log page (Home's 📋 play log, or the map editor's ⋯ → Play log…) reads them back:

  • First, ✖ what looks wrong: the lines that look like a failure, from all three files, in red. A Lua error (a line naming a script and a line number, such as …mobs.lua"]:2951: no prop named 'bolt') is always one, whatever its words. A line that comes again, such as a monster failing the same way at every shot, is listed once with its count, as in (×12). When there are none it says "✔ nothing in the logs looks like a failure".
  • Then each file in full.
  • At the top: ↻ read again, share the log (all three as one text file, for a bug report) and ▶ play again.

The page opens by itself when a launch fails. The way back from a play-test also says when the log has failures.

The iOS shell does not write the logs yet, and there is no iOS build of the studio.

  1. In the app, open a map and press ▶ Play. Watch the progress panel tick through its steps. Walk around, then use ◀ Studio to come back. You land on the same map, with the same view.

  2. Open 📋 play log from Home. Read the head of play-studio.log: it names the map you tested.

  3. Press share the log to see how you would send it with a bug report.

Export and import

⇪ export bakes the module and writes it as a pack: a zip of the module's folder, named id.zip. It is saved, or on a phone shared from the share sheet. Use it to back up a module, to move it to another device, or to send it to someone.

A pack holds every map of the module and everything it uses. To turn the module into a game people install and play, use the Packager instead.

⇩ import pack opens a pack someone exported. Only packs the studio wrote can be opened (they carry the module's studio documents). If a module with the same id is already here, the pack replaces it, and the studio takes a snapshot of the old one first.

In Gem Hollow Play in the map editor starts the map you have open. To play it as a player would, press ▶ play from menu on Home: menu is first by name, so it is the starting map. The title panel's Play takes you to world (the server has every map running), and its Quit, the quit_game node, brings a studio play-test back to the studio. In a packaged app the same button quits the app.

Snapshots

Undo is for the last few minutes. For anything older, the studio keeps snapshots: copies of the module kept on the device. Open them from Home's 🕘 snapshots, or from Settings.

When one is taken

  • When the module is opened, if the last snapshot is half an hour old or more.
  • Every ten minutes while you edit.
  • Before anything that replaces work: a pack imported over the module, a map deleted, a studio update changing it, a restore, or a sync bringing in changes from GitHub (named before sync from …; see Sync with GitHub).
  • By hand: ＋ snapshot now asks for an optional name.

A snapshot that would be the same as the latest is not taken.

Which are kept

The newest 20, then the first of each day for two weeks.

Restoring

Each snapshot shows when and why it was taken, its maps and its size, and "the same as now" if nothing has changed since.

  • restore brings back the whole module as it was.
  • ▾ maps lists its maps against the module now: the same as now, changed since, deleted since, or made since. A changed or deleted map has restore map, which brings back that map alone.
  • ✕ forgets a snapshot.

A restore takes a snapshot of the module as it is first, so you can always undo a restore.

Imported pictures, sounds and fonts are not copied into snapshots: megabytes every ten minutes would fill a phone. A snapshot lists their paths, and a restore tells you which of them are gone.

  1. Open 🕘 snapshots and press ＋ snapshot now. Name it before the boss.

  2. Open a map and delete a room.

  3. Back in snapshots, open ▾ maps on before the boss. The map says changed since. Press restore map.

  4. Notice the new snapshot at the top, taken just before the restore.

Settings

⚙ Settings (the sheet is titled Module settings) holds what module.txt says about the module:

SettingWhat it does
idthe module's folder name and identity: lowercase letters, digits, _ and -
name, aboutits name and a description
starting mapthe map the game starts on: Play on Home starts there, and so does a packaged game unless the Package page is told otherwise. the first by name means the first map in alphabetical order. Play in the map editor and on the rail still starts on the map being edited.
controlsplatformer — third person or first person (fps). First person puts the camera at the eyes and aims where the player looks; a shot goes to the middle of the screen, where a crosshair can be put on Screens. The module decides, not the player. A new module sets it from the kind of game you said it is.
show the debug overlay in the gamethe engine's numbers in the corner (tick, fps, position, prediction), the controls legend, and the swing and facing drawings. On unless you turn it off, which a shipped game wants. A new module starts with it off.
when I press Playthis device's choice for play-tests: as the module says, always show it or never show it. An exported pack always says what the module says.
levels keep their state, save and load games, survive a server restartwhich kinds of saving the module wants. Monsters are kept as they were, in the state they were in: a boss stays in its phase after a reload. See What the module keeps on its own.

In Cinderfall (Home → ◆ examples; see Getting started), levels keep their state is on, written as persist levels in module.txt. Its world is nine maps walked as one. If a district unloads, it comes back as the player left it when it loads again, with its doors open and its pickups taken, instead of reset. save and load games and survive a server restart are off. What the player has found in the whole game (keycards, Cores, valves, secrets, kills) is kept by the game graph progress, whose variables follow the player from map to map. Gem Hollow turns none of the three on: its game is one map.

Below them, 🕘 snapshots: the module as it was… opens the snapshots. Last comes Look — this device, not the module: the studio's own style, mode and pointer, the same card as Home's Style (see Getting started). It is not part of the module.

The Packager: an app from the module

The rail's 📦 Package page is the Packager, a bundled plugin. It turns the module into a game people can install: an app for Android, Windows, macOS or Linux. It builds the app in the page itself, from prebuilt engine kits, so the device needs no SDK, compiler or Docker. Nothing is uploaded.

The page opens with your module already in it: the studio bakes and packs it first. Then you work down its steps:

  1. Platform. Choose the target. For the desktops, the Desktop shell is Electron (self-contained) or Tauri (small, using the system's own web view). Load a kit file adds a kit the page does not have.
  2. The game. Its Name, Package id (Android) / bundle id (macOS) and Version; for Android, a Version code (must grow with every update) and the map it Starts on, which begins at the module's starting map from Settings. Studio chooses Game only or Game + studio, and Log file whether it writes one. An icon: Choose picture or Use the engine's.
  3. Signing key for Android: New key, Back up key, Restore key. Keep the key: an update must be signed with the same one.
  4. Build. The finished game is saved as a download.

The studio app carries the small kits: Android and the four Tauri desktops. The large Electron kits are not included, so on the studio's Package page the desktops build with Tauri unless you load an Electron kit.

PlatformWhat you get
Androida signed APK
Linuxa .tar.gz: unpack and run
Windowsa .zip with the game's .exe; not yet tested on real Windows
macOSa .zip with the .app, signed ad hoc

iOS is not a target yet.

The Packager also comes as a standalone tool of its own, for packaging a pack outside the studio. See Get the tools.

A macOS game you package is signed ad hoc and not notarized, so on another Mac its first launch shows the same warning as the studio's. Get the tools says how to get past it.

A play-test on your phone shows a black screen and nothing happens. Where do you look first?

  • The browser console
  • The engine's source code
  • The Play log page, starting with ✖ what looks wrong

A phone has no console. The Play log collects the studio's, the server's and the game's logs, and puts the lines that look like failures first.

You restore a snapshot from yesterday, then realise you wanted today's work after all. What now?

  • It's gone: a restore cannot be undone
  • Restore the snapshot taken just before the restore
  • Import the last exported pack

A restore snapshots the module as it is first, named before restoring …, so it can always be taken back.

You turn the debug overlay off in Settings, but set when I press Play to always show it. What does an exported pack do?

  • Launches clean, with no overlay: a pack says what the module says
  • Shows the overlay, because your device says always
  • Asks the player

The Play choice is only for your own play-tests on this device. The module's setting is what ships.
