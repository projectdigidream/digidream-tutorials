The language: Lua 5.1

The engine runs LuaJIT, which speaks Lua 5.1. The JIT compiler is switched off: compiled code would slip past the instruction budget, and measured on real levels it made no difference, because scripts spend their time calling into the engine. Lua tutorials on the web mostly teach 5.3 or 5.4. What is not there:

Newer LuaIn this engine
a // b (floor division)a syntax error; write math.floor(a / b)
& | ~ << >>syntax errors; use bit.band, bit.bor …
integers as a separate subtype, math.type, math.tointegerone number type, a double: whole numbers up to 2^53 are exact
the utf8 libraryabsent; strings are bytes and #s counts bytes
table.unpack, table.packabsent; unpack is a global
goto and labelsLuaJIT accepts them, but avoid them: the studio's checks and most readers do not expect them
_ENVabsent; Lua 5.1 has setfenv / getfenv

Which standard libraries are there, and which a strict server removes, is listed under Lua itself in Every function.

Where Lua lives, and which machine runs it

Each level has its own Lua machine, started when the level loads and thrown away when it unloads. Nothing is shared between levels: no variable, no table. There is also one game machine for the whole server.

You write it inRuns inWhen
📜 Scripts, + scriptevery level of the module, a copy in eachonce as the level loads, then whenever its hooks are called
Map settings → extra Luathat one map's levelonce as the level loads, last of all
A graph's action node set to do lua, or a trigger's lua actionthe level; in a game graph, the game machineeach time the run reaches it

The game machine runs only what the studio writes for you: the weapons, the player's sounds and the module's game graphs. There is no editor for hand-written game-wide Lua. A level script reaches the game through dnp.call_game; see State and bridges.

A do lua line is compiled once, when the level loads, as the body of a function. It sees one local, ev, the event that started the run (ev.entity, ev.target, ev.side, ev.sector, ev.ui_id, ev.widget_id, ev.value, ev.crush_kind). Returning false means "did nothing", which keeps a following once unspent.

Load order

When a level loads, its scripts run top to bottom, one file after another, in this order:

  1. The engine's runtimes the map needs: the monster runtime (mobs) when the module has monsters or weapons; the trigger runtime (triggers) when the map has triggers or a graph; the graph runtime (graphs) and the map's graphs when it has one.
  2. The module's monster definitions, then your 📜 scripts, in the order the Scripts page lists them. Each script is wrapped in do … end, so its locals are its own.
  3. The map's own file: its extra Lua, then its camera, the props and monsters placed in the editor, and its triggers.

So at the top of a 📜 script the map's props and monsters do not exist yet. Look them up inside a hook. A level has 16 script slots; Map settings shows how many are used.

When a saved level is being restored, the same files run, but dnp.restoring() is true while they do, and the placed monsters come from the save rather than from the map.

The game machine loads the weapon runtime and the module's arsenal, the player's sounds, and the trigger and graph runtimes with the game graphs, when the module has each of them.

Hooks

A hook is a global function with a name the engine knows, such as on_tick or on_prop_use. Define it with function on_tick(), never local function.

  • Collected per script. After each script loads, the engine takes the hooks it defined and adds them to a list. Then the global is cleared, so the next script can define its own.
  • All of them run. When the event happens, every script's handler runs, in load order. The runtimes register their own handlers the same way, so yours never replaces theirs.
  • Errors are separate. A handler that fails is reported and skipped; the others still run.
  • You cannot call a hook yourself after load: the global is gone. Put the work in a named function and call that from the hook.

on_player_enter and on_player_leave are only sent to the game machine. A level script notices arrivals by watching dnp.players() in on_tick.

The monster runtime also has a few callback fields you set rather than define: mobs.on_death, mobs.on_player_hurt, mobs.on_player_death. Those are single slots, not lists: the last script to set one wins.

Numbers and fx

Lua numbers are fine for counting: scores, ticks, indexes, health. Anything the world measures (positions, heights, speeds, distances) is fx, a fixed-point number that is exactly the same on every machine. A vec3 holds three of them.

  • Make one with fx.int(3), fx.frac(1, 4), fx.parse("2.5"); fx.approx(0.1) is the one door from a fraction, and it rounds.
  • Wherever the engine wants fx, a whole number or a decimal string is accepted too. A Lua fraction such as 0.5 is refused with an error.
  • + - * / mix fx with whole numbers. Comparisons do not: in Lua 5.1 p.z < 10 is an error and p.z == 10 is always false. Compare with fx.int(10).
  • x.int is the whole part (rounded down), tostring(x) the decimal.

Angles are brad: a whole number where 2^32 is a full turn (e:facing(), dnp.atan2, dnp.dir).

Determinism

The server's world must come out the same every time from the same inputs: that is what lets players' machines predict it, and saves load back exactly. So:

  • For chance, use dnp.random(lo, hi) (whole numbers, both ends included). It is seeded per level from the map. math.random is not.
  • For time, count ticks with dnp.tick(). There is no timer and no wait: keep a deadline (next_at = dnp.tick() + 120) and compare it in on_tick. os.time and os.clock read the real clock and differ every run.
  • For world maths, use fx and the engine's helpers (dnp.length, dnp.atan2, dnp.dir); math.sin and friends may differ in the last digits between machines.
  • Never let pairs order decide something the game can see. The engine's own lists (dnp.players(), dnp.props() …) come in a fixed order; walk them with ipairs.
  • Reads are immediate. Some writes (teleport, add_impulse, set_velocity, set_offset, change_map) are queued and land when the world steps.

Budgets

A level's Lua shares a tick of about 16 ms with everything else. The engine counts and caps it:

LimitPast it
2,000,000 instructions in one call (one hook handler, or one script's load)the call stops with instruction budget exceeded in '…' (2000000 per call / 8000000 per tick). pcall cannot catch it: the script makes no further progress
8,000,000 instructions in one tick, for all of a machine's handlers togetherthe same error, for every call left in that tick
256 MB of memory per machinethe allocation fails with an ordinary Lua error ("not enough memory")
4 ms of Lua in one ticknot stopped; a warning in the log: [lua] tick N: … us in callbacks (worst … us in on_tick in …)

The counts start again for every call and every tick, so a script that hit a limit runs normally next time. Keeping scripts fast lists the usual causes of the warning.
