Events and time

A script does nothing until the engine calls one of its hooks. This page lists every hook, shows how to notice what has no hook, and how to count time with nothing but the tick number.

You'll learnevery level hook and its arguments, why on_touch needs care, how to notice players arriving, one-shot, repeating and countdown timers, which writes wait for the next step, stale handles, keeping the game the same on every machine, and the budgets a script lives within Time35 minutes NeedsLua in the studio; the example Gem Hollow

Every hook

A hook is a global function with a fixed name. Define it in a 📜 script and the engine calls it. If several scripts define the same hook, each one runs, in load order.

HookArgumentsFires
on_tick()noneevery tick, 60 times a second, before the world moves
on_post_tick()noneevery tick, after the world has moved
on_prop_use(e, prop)who, which propa player presses use on a prop marked usable
on_touch(e, prop)who, which propevery tick while a body overlaps a prop
on_interact(e, side, sector)who, the wall's number, the room's numbera player presses use facing a wall flagged usable
on_cross(e, side, sector)who, the wall's number, the room's numbera body crosses a wall flagged trigger
on_attack(attacker, target)who swung, what it reached (an entity or a prop)a swing connects
on_crush(e, sector, how)who, the room, "vertical" or "pinned"the first tick a body is crushed
on_ui_event(e, ui_id, widget_id, value)who, which panel, which widget, its valuea player presses, flips, slides or picks on a panel your script opened (Panels)

There is no hook for a player arriving or leaving. Those go to the game machine only. A level script notices them by looking, as shown below.

The trigger and graph runtimes listen to the same hooks. Your on_prop_use runs as well as a graph's when_prop_used, never instead of it.

on_touch fires every tick

A player standing on a pad for two seconds calls on_touch 120 times. To act once per step onto the pad, remember the last tick each pair touched. A touch that comes right after the last one is the same touch going on.

Hold touch in the playground. The message comes once, however long you stay. Step off and on again and it comes again.

To know when someone steps off, check in on_tick for a key whose last touch is two or more ticks old. Recipe 2 does exactly that.

Noticing players arrive

dnp.players() is the list of players' entities right now. Compare it with the list you saw last tick. Do it in on_tick, and keep the work small, because it runs 60 times a second.

The first player arrives on the first tick. Press enter to bring in a second one.

e:index() is a slot in this level. It is fine for a level's own tables. A number that stays the same from level to level is e:player(). It is nil for anything that is not a player.

Timers from the tick

There is no timer function. There is a clock: dnp.tick(), the level's tick number. A tick is 1/60 of a second. To wait, store the tick you want and compare.

TimeTicks
1 second60
half a second30
1 minute3600

Three rules make timers safe:

  • Compare with >=, never ==. A level with nobody in it may sleep, and its on_tick does not run. When it wakes, the exact tick may be gone.
  • Set the variable to nil when a one-shot fires, or it fires every tick from then on.
  • Do the work only when something changes. The countdown sends the HUD a value once a second, not 60 times. (dnp.hud skips values that did not change anyway, but your own work adds up.)

dnp.hud(nil, { countdown = 4 }) sends a value to everyone in the level. It shows only where your HUD has an element bound to hud.countdown. More in Panels, HUD and camera.

Reads now, some writes later

When your script reads the world, it gets the value right now. Five changes are queued instead, and happen when the engine applies its queue, before the world moves:

QueuedIf you call it twice in one tick
e:teleport(v)the last one wins
e:set_velocity(v)the last one wins
e:add_impulse(v)both add up
s:set_offset(v) (a room)the last one wins
e:change_map(…)applied after every level has moved
 
e:teleport(vec3.new(10, 4, 0))
print(e:pos())   -- still the OLD position: the move is queued

So don't read back what you just wrote. Keep the value you wrote in a variable if you need it again.

Stale handles

An entity, prop or sector you get from the engine is a handle: a name for a slot, not the thing itself. When the thing goes (a monster dies and vanishes, a coin is picked up, a player leaves), the handle goes stale:

  • e:valid() returns false;
  • every getter returns nil;
  • every setter does nothing.

Nothing crashes, but e:pos().x on a stale handle tries to index nil, and that is an error. Check first:

if boss and boss:valid() then
  local p = boss:pos()
  …
end

Compare two handles by their index: a:index() == b:index(). And never save a handle (page 5): save what it stands for.

The same game on every machine

The server runs the world, and each player's game predicts parts of it. Moving rooms are worked out on each client from the tick. So anything that changes the world must come out the same every time:

  • Random numbers: use dnp.random(lo, hi). It gives a whole number from lo to hi, both included. It is seeded from the map, so a level replays the same way.
  • Maths that moves things: use fx and whole numbers. math.sin and other floating-point maths can differ in the last digit from one machine to another. They are fine for numbers that only go to a screen: a camera, a light level, a HUD.
  • Order: pairs visits keys in no set order. When the order changes the world (who gets the item first), loop with ipairs over a list instead.
local rolls = {}
for i = 1, 8 do rolls[i] = dnp.random(1, 6) end
print("eight dice: " .. table.concat(rolls, " "))

-- An exact fraction in fx: three quarters of 10 units.
local d = fx.frac(3, 4) * 10
print("three quarters of 10 is " .. tostring(d))

Budgets

A script shares the server with everything else, so the engine watches it:

LimitWhat happens past it
2,000,000 Lua instructions in one hook callthe call is stopped with instruction budget exceeded. pcall cannot catch it
8,000,000 instructions in one tick, for all of a level's scripts togetherthe same
256 MB of memory for a level's Luaallocation fails
4 ms of Lua in one ticka warning in the log: [lua] tick N: … us in callbacks (worst … us in …)

Two million instructions is a lot for one event. Hitting it nearly always means a loop that never ends. The 4 ms warning is the one to watch: a tick is about 16 ms, and the world needs most of it.

Try it in the studio

  1. Open Gem Hollow from Home → ◆ examples, then 📜 Scripts. Add a script called timers.

  2. Paste the arrivals script from above. Below it, add a repeating timer that prints dnp.player_count() every 5 seconds (300 ticks).

  3. Open the world map and press ▶ Play. Walk around for 20 seconds, then come back with ◀ Studio.

  4. Open 📋 play log. Find your arrival line, then the count every 300 ticks.

  5. Change your timer's >= to == and set the next tick to dnp.tick() + 300.5. Play again. The timer never fires again, because no tick is ever equal to a fraction. Put it back.

You want a sound when a player steps on a spring prop. You write dnp.sound(…) straight inside on_touch. What happens?

  • One sound per step
  • The sound starts again every tick for as long as they stand there
  • Nothing: on_touch is for monsters

on_touch fires every tick while the bodies overlap. Remember the last tick per pair, and act only when a touch starts.

In one hook you call e:teleport(spot) and then print(e:pos()). What is printed?

  • spot
  • nil, because the entity is moving
  • the position before the teleport

Teleports are queued and applied before the next step. Reads always see the world as it is now.

Which line picks a spawn point the same way every time the level starts?

  • local i = dnp.random(1, #spots)
  • local i = math.random(1, #spots)
  • local i = 1 + math.floor(math.sin(dnp.tick()) * #spots)

dnp.random is seeded from the map, so it is repeatable and the same on every machine.
