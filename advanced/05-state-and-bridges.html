State, saving and bridges

A script's variables live as long as its level. This page shows how to keep them longer, and how a script talks to graphs, triggers, the game and other maps.

You'll learnwhat the module's saving switches keep on their own, how to save your script's state with dnp.persist and a player's with dnp.persist_player, what dnp.restoring() is for, the store that outlives every game, reading and starting graphs and triggers, how far a level script can reach the game machine, and changing maps Time40 minutes NeedsTouching the world; it helps to know Variables, numbers and saving and The game graph, calls and maps; the example Gem Hollow

What the module keeps on its own

In Settings, three switches say what the module saves:

SwitchWhat it does
levels keep their statea level that unloads keeps its state, and gets it back when it loads again
save and load gamesone player can save to a slot and load it again (F5 / F9 in the game)
survive a server restartthe levels' states are written to disk and read back when the server starts

With any of them on, the engine keeps by itself: rooms that moved, wall pictures changed, room lights, textures and weather, the level's sky, and the props placed when the level loaded (where they are now, and which were taken). The monster runtime keeps living monsters, each with the state it was in, how far into it, its numbers and its cooldowns (as the time left), so a boss stays in its phase after a reload and carries on where it was. The graph runtime keeps graph variables.

Your script's own variables are not kept. When the level comes back, your script runs again from its first line. To keep something, hand it to the engine with dnp.persist.

dnp.persist: a level's state

local opened = {}   -- room tag -> true
local kills = 0

dnp.persist("my_arena", function()
  return { opened = opened, kills = kills }     -- save: plain data only
end, function(t)
  opened = t.opened or {}                        -- load: put it back
  kills = t.kills or 0
end)
  • The first argument is a name for this part. Make it unique in the module.
  • The engine calls save when it keeps the level: when the level unloads (with levels keep their state), for a save game, and every minute with survive a server restart.
  • It calls load when the level comes back.
  • save returns plain data: tables, numbers, strings, true and false, fx and vec3. A function or a handle is refused, by name. Save what a handle stands for instead: a prop's name and position, a room's tag.

dnp.restoring()

While a level is being put back, its scripts run with dnp.restoring() true. Anything they spawn while they load is held back, because the saved state brings back what was really there. So place things only on a fresh start, and let load put back the rest:

if not dnp.restoring() then
  -- a fresh level: set it up from scratch
  dnp.set_sector_light(0, 80)
end

Things you spawn later, in a hook, are not placements. Keep them through dnp.persist if they should come back.

dnp.persist_player: what a player carries

local found = {}   -- player index -> number of secrets

dnp.persist_player("secrets", function(e)
  return found[e:index()] or 0
end, function(e, n)
  found[e:index()] = n
end)

This part is about one player. It goes into a save game with the player, and comes back when that save is loaded. It needs save and load games, and a save game is for one player. It does not follow a player who walks into another level: each level's script keeps its own. A value that should follow the player everywhere belongs in a game graph.

The store: outlives every game

A save game is one moment. A new game forgets it. For things that should outlive both, such as a best time or what is unlocked, write to a store:

FunctionGives
dnp.store_save(name, value)true, or false and why
dnp.store_load(name)the value, or nil if nothing was ever saved
dnp.store_delete(name)true if there was one

A name is 1 to 48 letters, digits, _ or -. A value is plain data, at most 64 KB. The stores are the server's: in the app, on the device; on a server many people share, one for everyone.

The graph nodes save_vars and load_vars use the same stores. A graph's store is a table of variable names, so a script can read a graph's best time with (dnp.store_load("game") or {}).best_time.

Talking to graphs

A level's graphs and your script run in the same Lua machine, so they can reach each other:

FromToHow
scriptread a level graph's variablegraphs.var("pickups", "coins"): the graph's name, then the variable's
scriptstart a level graphgraphs.call("bonus", e, 5) starts its on_call nodes named bonus, with that entity and value
graphrun your Luaan action node, do lua, calling a global function of yours: give_bonus(ev.entity)
scriptstart a game graphdnp.call_game("graph_call", "bonus", 5, e): the name, the value, then the entity

The graphs table exists only in a level whose map has graphs. Check first: if graphs then … end. A script can't read a game graph's variables directly. Have the game graph call a level graph, whose do lua passes the value to your function.

Talking to triggers

The trigger runtime (Triggers in the map editor) keeps counters and named properties. A script can read them and set properties:

  • triggers.counter(name): a counter's value, 0 if never counted;
  • triggers.property(name), triggers.set_property(name, value): a named value;
  • triggers.is_enabled(name), triggers.is_spent(name): a trigger's state.

Like graphs, triggers exists only where the map has triggers or graphs.

The game machine

The game machine runs once for the whole server. In the studio, what runs there is written for you: the weapons, the player's sounds, and the game's graphs. You can't add your own Lua to it. A level script reaches it in two ways:

  • dnp.call_game("graph_call", name, value, e) starts the game graphs' on_call nodes of that name. This is the way to tell the game something: a secret found, a boss beaten.
  • dnp.game_has(name) says whether the game answers a call of that name at all.

Values cross as copies: numbers, strings, true and false, fx, vec3, tables, and entity and prop handles. A function is refused. For a score or quest flags that follow the player from map to map, let a game graph keep them, and call it from your script.

Changing maps

e:change_map(level, spawn_tag) sends a player to another map. level is a number: the map's place in dnp.levels(), counting from 0. spawn_tag names the spawn point to arrive at. With no arguments, it is the next map.

local function level_index(name)
  for i, n in ipairs(dnp.levels()) do
    if n == name then return i - 1 end
  end
  return nil
end

function on_prop_use(e, p)
  if p:name() == "sign_exit" then
    local to = level_index("menu")
    if to then
      dnp.screen(e, { fade = 1, fade_ms = 400 })
      e:change_map(to, "start")
    end
  end
end

The change is queued, and happens after every level has moved this tick. The player's panels from this level close. dnp.level() is the current level's number, in the same counting.

Try it in the studio

  1. Open Gem Hollow from Home → examples. In Settings, turn on save and load games.

  2. In Scripts, add a script called pulls:

    local pulls = 0

function on_prop_use(e, p)
  pulls = pulls + 1
  print("pulls: " .. pulls)
end

dnp.persist("pulls", function()
  return pulls
end, function(n)
  pulls = n
  print("restored pulls: " .. n)
end)

  3. Press Play on world. Use a lever twice, then press F5 to save. Use a lever once more, then press F9 to load.

  4. Come back and open play log. You see pulls: 1, pulls: 2, pulls: 3, then restored pulls: 2. Loading started the level's scripts again, and your load put the count back.

  5. Remove the dnp.persist call and try again. After F9, the next pull prints pulls: 1: the count started over with the level.

load runs after the top of your script, so it has the last word over a starting value. Saving is for one player: with two players connected, F5 is refused, and says why.

Your dnp.persist save function returns { boss = boss_entity }. What happens?

  • The boss comes back where it was
  • The save is refused: a handle is not plain data
  • It is saved as the boss's index

A handle names a slot that means nothing after a load. Save what it stands for, such as its kind and position, and spawn it again in load.

Where should a "best time" go, so that it outlives starting a new game?

  • dnp.persist
  • dnp.persist_player
  • dnp.store_save

persist parts belong to a game, and a new game forgets them. A store is kept on its own.

Your module's maps are menu, then world. Which call sends a player to world?

  • e:change_map(1)
  • e:change_map(2)
  • e:change_map("world")

The level is a number counted from 0, in the order of dnp.levels(). A helper that looks the name up is safer than a bare number.
