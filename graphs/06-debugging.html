Debugging graphs

A graph fails in one of two ways: it is refused, so it never loads, or it loads and quietly does something other than you meant. The studio catches most of the first kind before you press Play. For the second, you read the play log, and you narrow it down.

You'll learnwhat the studio refuses and where it tells you, how to read the play log and the engine's [graphs] lines, how the debug overlay helps, a checklist for "my graph does nothing", and the mistakes almost everyone makes once Time25 minutes Needsthe rest of this track; the app for Play (Play, export, snapshots)

What the studio refuses

A graph the engine would refuse does not load at all, and the rest of the level runs without it. That is the worst kind of bug: nothing happens and nothing looks wrong. So the studio checks every graph as you draw, with the engine's own rules, and says what the engine would refuse.

Where it says so

  • The graph window: a count of problems in red in the bar, and the problems themselves in red in the side panel.
  • ◇ Graphs: each row shows how many problems its graph has, and the first one.
  • Home: under to fix (N), one line per problem in the whole module. Tap a line to go there. With none, Home says nothing wrong that the studio can see.
  • Play and Export refuse to start while any graph has a problem. The status line names it: first's graph doors: ….

While you draw, the board refuses two links outright: an exec pin into a data pin (exec links to exec, data to data) and a node into itself (a node cannot feed itself). Everything else you can draw, and the list above tells you what is wrong with it.

The problem list names nodes by id: node 'open3'. The id is in the side panel when you pick a node. If the list is long, fix the first problem first: one missing sector can cause several lines.

The play log

Some things only the running game knows: which way a branch went, whether a value fit. For those, read what the game said. Each Play leaves three logs, started afresh every time:

FileWhat it holds
play-studio.logwhat the studio wrote and launched: the module.txt, the scripts each map declares (your graph files among them), what the bake warned about
play-server.logevery line of the game server, including every line the graph runtime prints
play-game.logthe game page's console: uncaught errors, refused messages, failed downloads

After a play-test, Home has a play log (map) button. The Play log sheet lists first the lines that look like a failure, under what looks wrong (N), then each log in full. ↻ read again reloads them, share the log hands all three over as one text file, and play again replays. The sheet opens by itself when a launch fails.

Play, and its log, need the studio app. In a browser, the studio exports a pack instead, and you run it with the engine and read the server's own output.

The engine's graph lines

Every line the graph runtime prints starts with [graphs]. Search play-server.log for it. The lines you will meet:

LineMeans
[graphs] doors: 12 nodes, 14 linksThe graph loaded. If this line is missing for a graph, it was not loaded at all.
[graphs] doors: 3 problems -- the graph is not loadedRefused. The lines just before it say why, by node id.
[graphs] doors: node 'm' was given 2.5 for 'height', which is not a fx -- skippedA linked value did not fit a trigger verb's argument, so the verb was skipped (a condition takes false).
[graphs] intro: node 'say' (subtitle) acted on no player -- the event's entity is not a player; tick `everyone` to reach them allA cutscene node had nobody to show to.
[graphs] doors: a run went past 256 steps at node 'x' and was stopped -- a loop?An exec loop with no delay in it.
[graphs] a call to 'ping' is 4 deep -- stopped (calls that call each other?)Calls that call each other in a ring.
[graphs] game: node 'go' calls a level with no entity to say which -- skippedA game graph's call to a level, from a run with no player.
[graphs] records: could not save store 'records': …A save_vars could not write.

The run-time lines (skipped, acted on no player, stopped -- a loop?) are said once per node, so the log is not flooded. They don't look like failures to the Play log sheet, so they may not appear under what looks wrong. Read the full play-server.log.

Your own log lines

The trigger action log writes a line of your own to the server log. In the node menu it is do log. Drop one onto a path to see whether a run gets there:

when_dies → do log "a death" → add_var kills → branch ─true→ do log "enough" → …
                                                      └false→ do log "not yet"

It is printf debugging, and it works. Take the logs out when you are done, or they fill the server log on a busy map.

The debug overlay

The engine can draw its numbers in the top-left corner of the game: the tick, the frame rate, your position, and the sector you stand in. That last one is the quickest way to check a when_sector_entered: walk into the room and read its number.

It is a module setting: in Settings, show the debug overlay in the game decides what the module ships. when I press Play overrides it for your own play-tests on this device: always show it, never show it, or as the module says.

Checklist: my graph does nothing

  1. Is it loaded? Look for [graphs] name: N nodes, M links in play-server.log. If it is missing, look for problems -- the graph is not loaded just above. And check the graph has a node: an empty graph is not written.

  2. Does the start node fire? Put a do log straight after it. If its line never appears, check its filters: the picked sector or side, the prop or kind name, and who (players by default). For a wall, check the wall is the one the player presses, and mark it usable.

  3. Does the run reach the action? Move the log along the chain. A run stops where an exit has no link: is the false of a branch the one taken? Is a once already passed (it is saved with the game)?

  4. Is the branch deciding on what you think? Put a do log on both of its exits, so the log says which way it went. (A do log's text has a data pin, but it takes text only: a linked number would be skipped.) Remember: 0 is true, and a value read earlier in the same run is remembered.

  5. Does the action reach the right thing? An unlinked entity is the event's. A linked one that yields nil does nothing. A cutscene node with no player to show to says acted on no player.

  6. Is it later than you think? A delay's far side runs later, and pending delays are dropped by a save and a load.

  7. Is it a cutscene? Use ▶ scene in the graph window to see the timing without playing.

A graph file edited by hand outside the studio names a node type that does not exist. What does the engine do with that graph?

  • Runs the parts that are fine
  • Refuses the whole graph; the rest of the level runs without it
  • Refuses to load the map

A graph that fails its checks does not load at all, and the server log lists the problems by node id. The level and its other graphs carry on.

Your when_sector_entered never fires. Which is the quickest first check?

  • A do log right after it, and the debug overlay's sector number as you walk in
  • Add a once
  • Change who to monsters

The log line tells you whether the start node fires, and the overlay tells you which sector you are really in.

Where do the engine's … -- skipped lines appear?

  • In red in the graph window
  • Only under "what looks wrong" in the Play log
  • In play-server.log, once per node, starting with [graphs]

They are run-time messages, so only the running server knows them. The studio can't see them while you draw.
