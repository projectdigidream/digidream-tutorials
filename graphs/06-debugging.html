Debugging graphs

A graph fails in one of two ways: it is refused, so it never loads, or it loads and quietly does something other than you meant. The studio catches most of the first kind before you press Play. For the second, you read the play log, and you narrow it down.

You'll learnwhat the studio refuses and where it tells you, the warnings it gives as you draw, how the game's own errors come back to the graph window after Play, how to read the play log and the engine's [graphs] lines, how the debug overlay helps, a checklist for "my graph does nothing", and the mistakes almost everyone makes once Time25 minutes Needsthe rest of this track; the app for Play (Play, export, snapshots)

What the studio refuses

A graph the engine would refuse does not load at all, and the rest of the level runs without it. That is the worst kind of bug: nothing happens and nothing looks wrong. So the studio checks every graph as you draw, with the engine's own rules, and says what the engine would refuse.

Where it says so

  • The graph window: a count of problems in red in the bar, and the problems themselves in red in the side panel. Each line names its node by id.
  • Graphs: each row shows how many problems its graph has, and the first one.
  • Home: under to fix (N), one line per problem in the whole module. Tap a line to go there. With none, Home says nothing wrong that the studio can see.
  • Play and Export refuse to start while any graph has a problem. The status line names it: first's graph doors: ….

While you draw, the board refuses two links outright: an exec pin into a data pin (exec links to exec, data to data) and a node into itself (a node cannot feed itself). Everything else you can draw, and the list above tells you what is wrong with it.

Warnings as you draw

Some mistakes would load and quietly do the wrong thing. The graph window names the node and says why, in red with the other problems, as you draw:

  • A despawn after a prop is touched or used. A touch or a use carries two things: the player who did it (entity) and the prop (prop, or target for a trigger word). do despawn left at its default takes entity, the player, whom a script cannot remove: the engine refuses, and the run stops there. So in a run that only ever starts from a prop, the studio now writes it as the prop, and its who? reads target -- the prop (default here). An unlinked remove after one when_prop_touched or when_prop_used takes the prop too. Where it would still take a player (a run that also starts from something else), the window says so: set who? to target, or link what to remove into entity.
  • An opening line from when_level_starts. The level starts before any player is in it, so a subtitle, fade, cutscene, camera or sound node there reaches nobody. The window says so, and suggests when_player_arrives with a once, or the game graph's when_player_arrives.
  • A second wire from an exec output. An exec output leads to one node, so a new wire from it replaces the old one. The board names the wire that went: an exec output leads to one node: the wire from … to … was replaced (undo puts it back; for both, add a sequence). One undo brings it back. To run both, put a sequence in between.

A word like the last one shows on the board itself for a while, as well as on the status line under the window; tap it to dismiss it.

The problem list names nodes by id: node 'open3'. The id is in the side panel when you pick a node. If the list is long, fix the first problem first: one missing sector can cause several lines.

The play log

Some things only the running game knows: which way a branch went, whether a value fit. For those, read what the game said. Each Play leaves three logs, started afresh every time:

FileWhat it holds
play-studio.logwhat the studio wrote and launched: the module.txt, the scripts each map declares (your graph files among them), what the bake warned about
play-server.logevery line of the game server, including every line the graph runtime prints
play-game.logthe game page's console: uncaught errors, refused messages, failed downloads

After a play-test, Home has a play log (map) button. The Play log sheet lists first the lines that look like a failure, under what looks wrong (N), then each log in full. A line that comes again is listed there once, with its count (×12), so one node failing on every pass does not hide the rest. A Lua error, a line that names a script and a line number, is always listed, whatever its words. ↻ read again reloads them, share the log hands all three over as one text file, and play again replays. The sheet opens by itself when a launch fails.

Play, and its log, need the studio app. In a browser, the studio exports a pack instead, and you run it with the engine and read the server's own output.

Back from Play: the game's errors in the graph window

When you come back from a play-test, what the game said about a graph is in its window too, with the other problems, naming the node that failed: node 'x': in the last play-test, the game said: … (and (×12) when it said so twelve times). You no longer have to open the Play log to find it. The line goes once you change that node, and all of them go at the next Play.

The run-time lines (skipped, acted on no player, stopped -- a loop?) are said once per node, so the log is not flooded, and the Play log sheet lists each of them under what looks wrong. The load line (12 nodes, 14 links) is not a failure, so it is only in the full play-server.log.

Your own log lines

The trigger action log writes a line of your own to the server log. In the node menu it is do log. Drop one onto a path to see whether a run gets there:

when_dies → do log "a death" → add_var kills → branch ─true→ do log "enough" → …
                                                      └false→ do log "not yet"

It is printf debugging, and it works. Take the logs out when you are done, or they fill the server log on a busy map.

The debug overlay

The engine can draw its numbers in the top-left corner of the game: the tick, the frame rate, your position, and the sector you stand in. That last one is the quickest way to check a when_sector_entered: walk into the room and read its number.

It is a module setting: in Settings, show the debug overlay in the game decides what the module ships. when I press Play overrides it for your own play-tests on this device: always show it, never show it, or as the module says.

Checklist: my graph does nothing

  1. Is it loaded? Look for [graphs] name: N nodes, M links in play-server.log. If it is missing, look for problems -- the graph is not loaded just above. And check the graph has a node: an empty graph is not written.

  2. Does the start node fire? Put a do log straight after it. If its line never appears, check its filters: the picked sector or side, the prop or kind name, and who (players by default). For a wall, check the wall is the one the player presses, and mark it usable.

  3. Does the run reach the action? Move the log along the chain. A run stops where an exit has no link: is the false of a branch the one taken? Is a once already passed (it is saved with the game)?

  4. Is the branch deciding on what you think? Put a do log on both of its exits, so the log says which way it went. (A do log's text has a data pin, but it takes text only: a linked number would be skipped.) Remember: 0 is true, and a value read earlier in the same run is remembered.

  5. Does the action reach the right thing? An unlinked entity is the event's. A linked one that yields nil does nothing. A cutscene node with no player to show to says acted on no player.

  6. Is it later than you think? A delay's far side runs later, and pending delays are dropped by a save and a load.

  7. Is it a cutscene? Use scene in the graph window to see the timing without playing.

In Gem Hollow

Open the bundled example, Gem Hollow, and break its levers graph on purpose (on the world map). Each lever runs one chain: when_prop_used → once → a lever animation → a camera_flythrough along path 2 → open_door with tag 11 → a subtitle. Undo each break before you try the next.

A link the studio catches

Pick the red lever's open_door node and clear its tag. The door is now tied to nothing, and the engine would refuse the whole graph. Home lists it under to fix (N):

world: graph levers: node 'opendoor7': a open_door needs a sector -- picked on the map, linked from sector_of, or a tag

Play refuses to start until you fix it. Tap the line to go to the graph. Delete camera path 2 from the map instead, and you get node 'cameraflyt6': no camera path with tag 2 on this map (Camera → camera paths). The graph didn't change, but the map it needs did.

A link nobody catches

Now give the red lever's when_prop_used a misspelt prop, such as lever_rd. Nothing checks prop names, so Home says nothing wrong that the studio can see. Play starts, and play-server.log still says the graph loaded:

[graphs] levers: 39 nodes, 36 links

You pull the lever and nothing happens. The what looks wrong list is empty, because nothing failed: the start node never matched. This is step 2 of the checklist. Put a do log straight after the start node and play again. If its line never shows up, the start node's filter is wrong.

A value that does not fit

The vault graph counts keys in the variable keys, and its compare asks keys >= 3 before the vault opens. Type 2.5 into its b instead. A typed decimal is kept as text, and comparing a number with text is always false, so the vault never opens. The studio says nothing about it, and neither does the log. Keep compared numbers whole (see the table below).

A graph file edited by hand outside the studio names a node type that does not exist. What does the engine do with that graph?

  • Runs the parts that are fine
  • Refuses the whole graph; the rest of the level runs without it
  • Refuses to load the map

A graph that fails its checks does not load at all, and the server log lists the problems by node id. The level and its other graphs carry on.

Your when_sector_entered never fires. Which is the quickest first check?

  • A do log right after it, and the debug overlay's sector number as you walk in
  • Add a once
  • Change who to monsters

The log line tells you whether the start node fires, and the overlay tells you which sector you are really in.

During a play-test the server said node 'm' was given 2.5 for 'height', which is not a fx -- skipped. Where do you see it when you come back to the studio?

  • Only in play-server.log
  • In that graph's window, as a problem naming node m, as well as in the Play log
  • On Home, under to fix

The game's lines about a graph come back to its window, naming the node that failed, until you change that node or play again. They are in play-server.log and the Play log sheet too.
