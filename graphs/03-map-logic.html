Map logic recipes

Five graphs that most action maps need, wired node by node with nothing but real nodes. Build them as written, then bend them to your map.

You'll learnhow to build a key-locked door, a secret that counts, an ambush, a wave arena that opens its exit, and a timed switch puzzle, and the traps each one hides Time45 minutes Needsa map with a few rooms and a door (Your first map), a monster (Your first monster), and Variables, numbers and saving

How to read a recipe

Each recipe has a table of nodes and a list of links. The id is a short name for the node in this page; the studio gives its own ids, and you can ignore them. Fields are what you set in the side panel. A field that says picked is tapped on the map: the board steps aside while you tap a room, a wall, or a spot on the floor.

Links are written from.pin → to.pin. White (exec) links come out of then, true, false, 0, 1 … and go into in. Everything else is a data link.

Put each recipe in its own graph: + new graph on map in ◇ Graphs, named keydoor, secrets and so on. Each graph uses one of the map's script slots, so on a busy map you can also put two recipes in one graph. They don't interfere: each start node has its own runs.

Warm-up: the shape of an ambush

The lab is loaded with an ambush: entering sector 3 shuts the door behind you, sounds an alarm, and opens the door three seconds later. Press 🚶 player enters sector 3 twice. The second time, once stops the run at once.

Recipe 1: a key-locked door

There are no key items in the graph vocabulary, so the graph keeps the key itself: a variable. Touching the key prop sets it and removes the prop. Using the door checks it.

Before you start: in Props, press + new prop and name it red_key. Turn solid off, so the player can walk into it. Place one in the map. Make the door a narrow room whose ceiling sits on its floor, as the 🚪 door preset would, but don't use the preset.

Variables: has_red_key, starts at false.

idNodeFields
takewhen_prop_touchedprop: red_key · who: players
gotset_varvar: has_red_key · value: true
goneremove(entity linked)
dingplay_soundsound: a pickup sound
tellsubtitletext: You have the red key.
presswhen_wall_usedside: picked, the door's face on the near side
press2when_wall_usedside: picked, the door's face on the far side
keyget_varvar: has_red_key
ifbranch
openopen_doorsector: picked, the door · close_after: 4
nosubtitletext: You need the red key. · seconds: 2
 
take.then  → got.in
got.then   → gone.in
take.prop  → gone.entity        (data: remove the key, not the player)
gone.then  → ding.in
ding.then  → tell.in
press.then → if.in
press2.then → if.in             (an exec input takes many links)
key.value  → if.cond
if.true    → open.in
if.false   → no.in
  • The data link into gone.entity matters. Unlinked, remove would act on the event's entity: the player. The prop is a different output of the start node.
  • open_door with close_after shuts the door again after 4 seconds. Without it, the door stays open.
  • The key is the level's, not the player's: in co-op, once anyone has it, the door opens for all. It is also forgotten when the level starts again, unless the module keeps level state.

The DOOM modules carry keys of their own (key_red and friends), picked up and checked by their Lua. A graph can't see that inventory. This recipe is for your own keys in your own module.

Recipe 2: a secret that counts

Walking into a hidden room counts once, says so, and shows the count on the HUD.

Variables: secrets, starts at 0.

idNodeFields
foundwhen_sector_enteredsector: picked, the secret room · who: players
firstonce

nget_varvar: secrets
hudset_hudname: secrets · to: everyone
saysubtitletext: A secret! · seconds: 2
chimeplay_soundsound: a chime
 
found.then → first.in
first.then → count.in
count.then → hud.in
n.value    → hud.value
hud.then   → say.in
say.then   → chime.in
  • For a second secret, add another when_sector_entered and another once, and link that once's then into the same count.in. Each secret has its own once; they share the counter.
  • set_hud writes the HUD value secrets. It shows only where a layout or a panel has a text with {hud.secrets} in it. Add one in Screens (see Sky, screens and weather).
  • To count secrets across the whole game, add a call after count (to: game, name: secret_found) and keep the total in a game graph. See The game graph, calls and maps.

Recipe 3: an ambush

The player walks into a room, the door slams behind them, and imps appear.

There is no node that wakes a sleeping monster placed on the map. A dormant monster wakes by its own brain (see The brain). A graph's ambush spawns its monsters instead; a spawned monster starts awake.

idNodeFields
enterwhen_sector_enteredsector: picked, the trap room · who: players
firstonce
shutclose_doorsector: picked, the door you came in by · speed: fast
boomcamera_shakestrength: 0.4 · seconds: 0.5
threesequencecount: 3
aspawnwhat: imp · x, y, z: picked, a dark corner
bspawnwhat: imp · x, y, z: picked, another corner
yellplay_soundsound: a roar · (entity linked)
 
enter.then → first.in
first.then → shut.in
shut.then  → boom.in
boom.then  → three.in
three.0    → a.in
three.1    → b.in
three.2    → yell.in
b.entity   → yell.entity        (the roar comes from the second imp)
  • sequence runs 0, then 1, then 2, in the same tick. By the time 2 runs, b has spawned, so its entity output is the new imp.
  • Give spawn its z: picking a spot on the floor fills x, y and z. Without z it spawns at height 0, which may be inside the floor or the void.
  • If a spawn fails (no room), its entity is nil, and the linked play_sound does nothing rather than roaring from the player.

Recipe 4: an arena that opens when all are dead

Two waves of three. When the last monster of the last wave dies, the exit opens. This joins recipe 3 with a counter.

  • Why fighting? when_dies fires for every monster that dies in the level. The flag makes the counter listen only while the arena is on. If the arena has its own monster, set kind on dies instead, or as well.
  • Why the delay loop is safe: rest.then → next.in goes back up the chain, but each pass after a delay is a new run, so it never meets the 256-step limit. The again branch ends it.
  • Why left reads the new value: the cleared branch pulls left after down has run, and nothing in this run read alive before.
  • Who sees the win line? In a when_dies run, the event's entity is the monster that died, not a player. An unlinked subtitle would reach nobody, and the server log would say acted on no player. Tick everyone on win, or link dies.by (the killer) into its entity.

Recipe 5: a timed two-switch puzzle

Two switches, far apart. Each one lights up for five seconds when pressed. If both are lit at once, the vault opens.

Before you start: pick two textures, one for an unlit switch and one for a lit switch. Mark both walls usable in their wall flags.

Variables: a_on (false), b_on (false).

idNodeFields
pressAwhen_wall_usedside: picked, switch A
isLitAget_varvar: a_on
guardAbranch

lightAset_wall_textureside: picked, switch A · texture: the lit one
seqAsequencecount: 2
waitAdelayticks: 300
clearAset_varvar: a_on · value: false
darkAset_wall_textureside: picked, switch A · texture: the unlit one
The same nine nodes again for switch B, with b_on.
chkAget_varvar: a_on (a second node, not isLitA)
chkBget_varvar: b_on (a second node, not isLitB)
bothlogicop: and
checkbranch
vault1once
vaultopen_doorsector: picked, the vault door · speed: slow
 
pressA.then  → guardA.in
isLitA.value  → guardA.cond
guardA.false → setA.in          (guardA.true unlinked: already lit, ignore)
setA.then    → lightA.in
lightA.then  → seqA.in

seqA.1       → waitA.in
waitA.then   → clearA.in
clearA.then  → darkA.in

chkA.value   → both.a
chkB.value   → both.b
both.value   → check.cond
check.true   → vault1.in
vault1.then  → vault.in
  • The guard ignores a press on a switch that is already lit. Without it, a second press would start a second timer, and the first timer would put the light out early.
  • The sequence does the check first (exit 0), then starts the timer (exit 1), both in the same tick.
  • Why chkA is a separate node: in a run from switch A, isLitA was read at the guard, while a_on was still false. A pure node is worked out once per run, so reading isLitA again in the check would still say false. A fresh get_var reads the value setA just wrote.
  • Five seconds is 300 ticks. To make the window shorter for a harder puzzle, lower both delays.

Exercise: build the key door

  1. Make the red_key prop in Props (solid off), and place it in a room away from the door.

  2. In ◇ Graphs, press + new graph on your map and name it keydoor. Add the variable has_red_key and set its starts at to false.

  3. Build the pickup half: take, got, gone, ding, tell. Don't forget the data link take.prop → gone.entity.

  4. Build the door half. For press, tap the door's face on the map when the side panel asks for the wall. Add press2 for the other face.

  5. Check that the window's bar shows no problem count. If it does, read the first line in the side panel.

  6. Play. Press use on the door: the line says you need the key. Fetch it and try again.

In the key recipe, you forget the link take.prop → gone.entity. What does remove do?

  • Removes the key: it is what was touched
  • Acts on the event's entity, the player who touched the key
  • Nothing

Unlinked, an entity input means the event's entity, and for a touch that is whoever walked in. The prop is a separate output.

Why does the arena check fighting before counting a death?

  • Because when_dies fires for every monster that dies anywhere in the level
  • Because a dead monster's entity is nil
  • Because add_var cannot go below zero

Without the flag, a monster killed elsewhere before or after the fight would change the count.

In the switch puzzle, the check reads isLitA (the guard's own get_var) instead of a new chkA. Pressing B then A within five seconds…

  • opens the vault
  • is refused by the studio
  • does not open the vault: in A's run, isLitA was already read as false at the guard

A pure node is worked out once per run. The read at the guard, before setA, is the value the whole run sees.
