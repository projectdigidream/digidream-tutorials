Variables, numbers and saving

A graph remembers things in variables, and reads and changes the world's bodies through their properties. This page covers both, the numbers that flow between them, and exactly what is still there after a save, a reload or a new game.

A graph's own variables

Open the side panel's variables tab (on a phone, the 𝑥 tab in the bar). The first list, this graph's variables, is yours:

  • + variable asks for a name. Letters, digits and underscore are kept; anything else is dropped. The new variable starts at 0.
  • Change its starts at to a number (3), a word (red), or true or false. The studio reads what you type the way you meant it: true is true/false, 12 is a number, abc is text.
  • The ✕ on its row removes it.

Three nodes use variables: get_var reads one, set_var sets one, and add_var adds to a number. Their var is a dropdown. Each row of the variables tab also has buttons that drop these nodes onto the board, already filled in.

Whose variable is it?

  • Each graph has its own. Two graphs can each have a count, and they are two different variables. To share a value between graphs, pass it with a call.
  • Everyone in the level shares them. A variable is not per player. If one player picks up a key and you set has_key to true, the door opens for everyone in that level. That is usually right in co-op. For a truly personal value, use a property of the player (below), or Lua.
  • A map's variables start again when its level does. The game's graphs keep theirs from level to level (see The game graph).

A variable may not take a property's name. + variable refuses hp with hp is an entity's property (in the list below) -- a variable needs another name, because the engine would refuse the whole graph.

Properties: reading and changing bodies

Under your variables, the same tab lists every property an entity has. get_var, set_var and add_var reach them by name, just like variables. Their entity pin says whose property: unlinked, it is the event's entity; linked, it is that one. (For your own variables the pin is dimmed, because it means nothing there.)

Setting a movement rule

  • On a player, setting a movement rule makes a lasting effect, and a later set replaces it. The engine never lets a script rewrite a player's body directly, because the player's own machine predicts their movement and must agree.
  • On anything else, it is written straight into the body.

The dropdowns only offer what each node may use: set_var offers only settable properties, and add_var only settable numbers. The studio says what the engine would refuse at load: … can only be read -- a graph cannot set it, … is not a number, so nothing can be added to it.

Counters

A counter is a number variable, an add_var that adds to it, and a compare that reads it.

when_dies ──then──▶ add_var kills +1 ──then──▶ branch ──true──▶ open_door
                                                 ▲ cond
              get_var kills ──value──▶ compare (a >= 5) ──value──┘
  • add_var's value can be negative: -1 counts down.
  • compare has op (==, ~=, <, <=, >, >=) and two inputs, a and b. Each can be typed or linked. ~= means "is not".
  • The compare reads kills after the add, because the branch pulls it only when the run reaches the branch.

Trigger cards have their own counters (counter_add, counter_at_least), kept per map in the trigger table. They are a separate store from a graph's variables: a counter_add on kills does not change a graph variable called kills. Pick one of the two for each count.

True and false

A variable can hold true or false: door_open, boss_awake, has_key. Set it with set_var (type true or false into its value), and test it with branch.

logic combines them. Its op is and, or or not; not reads only a.

branch takes true for anything that is not false or nil. The number 0 is true, and so is empty text. To ask "is the count zero?", compare it: compare a == 0 into the branch.

Comparing two different kinds is safe but rarely useful. == between a number and text is just false. Ordering (<, > …) a number against anything that is not a number is always false.

Numbers

In the world's nodes, numbers are plain: map units for distances, seconds for times, degrees for angles, and slow, normal or fast for speeds. Two exceptions count in ticks, 60 a second: delay's ticks and the pain_ticks property.

  • math does +, -, *, /, min and max. Division by zero gives 0, not a crash.
  • random gives a whole number from lo to hi, both included. It draws from the level's own random stream, so a replayed level draws the same numbers. It draws once per run: two nodes reading one random see one number.

A number from a variable

Almost every number a node takes is also a data pin of the same name, so a variable, a property or a sum can feed it. In the side panel, the 𝑥 beside a numeric field does it without drawing: tap it and choose a variable or a numeric property. ✕ makes it a typed number again. The exception is sequence's count, which decides how many exits the node has and so has no 𝑥.

Start nodes take linked numbers too (every's seconds, when_near's radius), with one rule: the value is worked out afresh each tick, from pure nodes only, because no run exists yet to make it. An every whose period comes from a variable takes the new period from the next tick.

Fixed point

The engine's simulation does not use ordinary floating-point numbers. Positions and heights are fixed point (32 bits whole, 32 bits fraction), so every machine computes exactly the same thing. In 0.1, floating point is already slightly wrong, so the engine is strict about what it takes:

  • A trigger action's fixed-point argument (a sector_move's height, a teleport's x) takes a whole number or an exact decimal typed as text. When you type 2.5 into a field, the studio keeps it as the exact text 2.5, which is right.
  • A linked value that is a fraction, such as the result of math 1 / 3 or math 5 * 0.5, does not fit. The action is skipped, and the server log says once: node '…' was given 2.5 for 'height', which is not a fx -- skipped.
  • The world nodes (teleport, move_floor, push …) convert plain numbers for you. Fractions are fine there.

Decimals typed into a graph are kept as exact text. That suits fixed point, but not compare: compare a >= 2.5 compares a number with the text 2.5, and ordering against text is always false. The same goes for a variable whose starts at is 0.5, until an add_var makes it a number. Keep compared numbers whole: count in tenths (25, not 2.5), or pass the decimal through a math node (2.5 + 0) to make it a number.

What survives

Three switches decide what the game keeps. They are module settings: open Settings from Home, and the Module settings sheet has:

Togglemodule.txtWhat it does
levels keep their statepersist levelsA level that unloads keeps its state, and gets it back when it loads again, instead of starting over.
save and load gamespersist savesOne player can save to a slot and load it again (F5 / F9 in the game).
survive a server restartpersist serverLevel state is written to disk every minute and on stop, and read back at start.

When a level's state is kept, each of its graphs keeps, under the graph's name:

  • its variables;
  • which of its once nodes have passed.

On a load, a saved variable is restored only if the graph still has a variable of that name and the same type. A variable you renamed, or changed from a number to a word, starts fresh. The state is kept under the graph's name, so renaming the graph starts all of its saved state over.

What is not kept: pending delays, and anything half done. A door caught half open comes back half open, but the delay that would have shut it is gone. The engine keeps the world's own state too: sectors moved, switch pictures, and the looks a graph set with set_sector_light and friends.

Saved on disk, on purpose

A save game is the world at one moment, and a new game forgets it. A high score, an unlocked level or a setting should outlive both. Three nodes, in the menu's other group, write variables to a store on the disk:

  • save_vars writes variables to a store. store defaults to game; vars is a comma-separated list, all the graph's variables by default. It writes beside what the store already holds, so several graphs can share one store. Its failed exit runs when there is nowhere to write, a value can't be kept, or the store would pass 64 KB.
  • load_vars reads them back into the graph's own variables, only into one of the same kind (a number into a number). Its none exit runs when nothing was ever saved there.
  • forget_saved deletes a store: a progress reset.

Only numbers, text and true/false are kept. A store name is 1 to 48 letters, digits, _ or -. The stores belong to the server: on a server several players share, they are the server's, not each player's. In the desktop app they live in your user data folder; on Android, in the app's own files.

A player's own identity and inventory carried between servers (docs/PERSISTENCE.md) is designed but not built. Nothing today follows a player from one server to another.

Exercise: a best time that survives

  1. Open ◇ Graphs, press + new graph for the game and name it records. In the variables tab, add best (starts at 9999) and last (starts at 0).

  2. Add when player arrives. Link it to a load_vars with store records and vars best. Leave its none exit unlinked: the first time, best keeps its start.

  3. Add an on_call named finished. A level will call it with the run's time as its value (page 5 shows the calling side). Link its then to a set_var last, with value linked from the on_call's value.

  4. After it, a branch whose cond is a compare: a from a get_var last, op <, b from a get_var best.

  5. On true: a set_var best with its value linked from the same get_var last, then a save_vars with store records and vars best.

  6. Check the side panel shows no problems. Then think through a new game: best starts at 9999, and the load_vars on arrival brings the saved record back.

A compare has op >= and you typed 1.5 into its b. a is linked to a variable holding 3. What does it give?

  • true, since 3 is at least 1.5
  • false: the typed decimal is kept as text, and ordering a number against text is false
  • the graph is refused

Decimals typed in a graph stay exact text, for fixed point. Keep compared numbers whole, or turn the text into a number with a math node.

A level's graph is waiting in a 10-second delay when the player presses F5. After F9, what happens?

  • The delay finishes its remaining seconds
  • The delay starts again from 10 seconds
  • Nothing: pending delays are not saved

A save keeps state (variables, passed once nodes), not what was in the middle of happening.

You set move_speed on the player with set_var. What really happens?

  • A lasting effect is put on the player, and a later set replaces it
  • The player's body is rewritten directly
  • Nothing: movement rules are read only

The engine never lets a script rewrite a player's body, because the player's machine predicts their movement. Setting a rule on a player is an effect, one per player and rule.
