The game graph, calls and maps

A map's graph lives and dies with its level. A game graph runs once for the whole game, and remembers across every map. This page shows how the two talk, how players move between maps, how many graphs a map can hold, and where graphs stop and Lua begins.

You'll learnwhat a game graph can and cannot do, how call and on_call carry a value across, how to send a player to another map and greet them there, the map's 16 script slots, what a save keeps of the game, and the ways into Lua Time35 minutes NeedsVariables, numbers and saving; a module with two maps for the last part

Two places a graph can run

In ◇ Graphs, the list starts with the game's graphs and their + new graph for the game, then one group per map with + new graph on map. Under the hood they run in different places:

A map's graphA game graph
Runs inthat map's level, once per levelthe game, once, not in any level
Variablesstart again with the level (unless the module keeps level state)kept from level to level; saved with the game
Can toucheverything in its level: sectors, walls, spawns, triggersplayers and their view; nothing that needs a level's map
Hearseverything that happens in the levelplayers arriving and leaving, every tick, props touched and used, panels, buttons, weapons
Costsone of the map's script slotsno slot

The game has no level of its own. When something happens to a player, the game is bound for that moment to the world of the player it is about. That is why it can speak to a player (a panel, the music, a fade, a subtitle) but cannot name a sector: whose sector would it be?

What a game graph may use

Its node menu only offers what works there:

  • Start nodes that aren't tied to a level: when_player_arrives, when_player_leaves, every, after, when_prop_used, when_prop_touched, when_button_pressed, when_panel_used, the weapon events, on_call. Of the trigger events: on_tick, on_touch, on_prop_use, on_ui_event, on_player_enter, on_player_leave.
  • Actions on entities and on a player's view: damage, heal, push, play_sound, the panel nodes, the cutscene nodes, camera_follow, camera_shake, weapons, change_map, quit_game, the storage nodes. Of the trigger actions: set_hp, set_solid, set_animation, despawn, add_effect, music, ui_open, ui_close, camera, screen, counter_add, counter_set, set_property, log, lua.
  • All of flow and data.

Everything marked level only in Every graph node is refused: doors, floors, spawn, teleport, when_sector_entered, when_dies, camera paths, the sky. The studio says a … acts on a level, and the game has none -- call the level's graph (a call node, to level) and do it there. The other way round, a map's graph refuses the game's own events: 'on_player_enter' reaches only the game's graph. (when_player_arrives works in both.)

Calls: crossing over

A call node starts every on_call node of the same name, now, and then carries on. It sends one value and one entity.

toFrom a map's graphFrom a game graph
gamethe game's graphsthe game's own graphs
levelthis level's own graphsthe graphs of the level that entity is in
  • entity is the one linked, or else the event's. A call to: level from the game needs an entity, to know which level. Without one it is skipped, and the log says calls a level with no entity to say which -- skipped.
  • value is typed, or linked. Numbers, text, true/false and entity handles cross safely.
  • On the far side, on_call's outputs entity and value are what was sent. Its run is a run like any other.
  • Every graph with an on_call of that name answers, in the order they were loaded.
  • Calls nest at most four deep. Two graphs that call each other in a ring stop there: a call to '…' is 4 deep -- stopped (calls that call each other?).

The Graphs list shows, for each graph, what it calls and what it answers. A call nobody answers is a warning under the list, and a problem on Home: … calls 'x' (to game), and no game graph has an on_call of that name.

Example: a game-wide secret count

Each map counts its own secrets (Recipe 2). The game keeps the total, so the HUD shows every secret found on every map.

map01's graph "secrets":
  when_sector_entered → once → call (to: game, name: secret_found, value: 1)

the game's graph "progress"      vars: total = 0
  on_call secret_found → add_var total (value ← on_call.value) → set_hud (name: secrets, value ← get_var total)

The set_hud goes to the on_call's entity: the player whose map made the call. That works because the map's call sent the event's entity, the player who walked in.

Example: the game asks a level to act

A main menu panel is opened by the game's graph. Its Start button should open a gate in whatever map the player is on. The game cannot name the gate, but the level can:

the game's graph:
  when_panel_used (menu › start) → close_panel (menu) → call (to: level, name: open_gate)

each map's graph:
  on_call open_gate → open_door (sector: picked, that map's gate)

The call's entity is the panel event's player, so the call goes to that player's level. Maps without an open_gate simply don't answer.

Going to other maps

change_map sends a player to another map. It is in the menu's maps group.

  • level: the map, chosen from the module's maps. A map the module does not have is a problem: no map called … in the module.
  • spawn: the spawn point to arrive at on that map, by its tag (the door on the far side). Spawn points are placed in the map editor; each has a tag. Without one, or with a tag the map lacks, the player arrives at the map's start, and the studio warns you.
  • fade: seconds of fading to black first. The new map fades in on arrival.
  • everyone: every player in the level, not just the event's.

On the far side, when_player_arrives in that map's graph starts a run for the newcomer: the place for a title card or a door that shuts behind them. change_map works from a game graph too.

teleport with a spawn tag moves a player to a spawn point on the same map. quit_game closes the game for the player: the main menu's Quit. In the desktop app it exits; in a play-test it goes back to the studio; in a browser tab the screen fades to black and says the game may be closed.

A module can also lay its maps out on a grid as one connected world (the maps' metamap), where neighbouring maps share one simulation and the player walks from one into the next. Each map's graphs still run in their own map's level. Be sparing there with who: monsters or anyone on the "when …" nodes: they watch every body in the level on every tick, and a big world has many.

Script slots

A map may declare at most 16 scripts, and each of its graphs is one. The rest go to what the map needs to run:

SlotsForWhen
2the monster runtimethe module has monsters or weapons
2the trigger runtimethe map has triggers or any graph
2the graph runtimethe map has a graph
1 eachthe map's graphseach graph with at least one node
1the module's own Lua (monsters, scripts)the module defines any
1the map's own Lua (placed things, triggers)always

So a map in a module with monsters can hold 8 graphs. Play and Export refuse a map past the limit: a map can declare 16 scripts and this module needs 17: …. An empty graph is kept in the studio but not written, so it costs nothing. Game graphs take no map slots. When you run short, merge small graphs: one graph can hold many unrelated chains.

What the game keeps

  • A game graph's variables and its passed once nodes go into every save game, as the game's own part, under the graph's name.
  • With survive a server restart on, they are also written to the server's game.save every minute and on stop, and read back before any level loads.
  • A new game starts the game's graphs from scratch. What a graph wrote with save_vars is the exception: it outlives a new game.

So a score, quest flags and unlocked doors belong in a game graph. A map's own puzzle state belongs in the map's graph, kept by levels keep their state.

Graphs or Lua?

Graphs cover most map logic. Reach for Lua when you need what the vocabulary does not say:

  • a value per player (graph variables are shared by the level);
  • going over many entities at once ("every monster within 10 units");
  • maths beyond + - * / min max, or building text;
  • a new behaviour for a monster or weapon that their workshops can't express.

There are three ways in, from small to large:

  1. do lua, the trigger action lua, as a node. Its code is a snippet that runs with ev, the event (ev.entity, ev.sector …).
  2. 📜 Scripts: the module's own Lua files. A script runs in every level, after the module's monsters are loaded, and its hooks run alongside everyone else's. See Graphs.
  3. Calling a graph from Lua. A level's script can start that level's on_call nodes with graphs.call("name", entity, value), and the game's with dnp.call_game("graph_call", "name", value, entity). So Lua can do the hard part and hand the result to a graph.

A do lua written in the studio is stored as text and compiled with loadstring. A server running in its strict trust profile removes loadstring, and then refuses the code at load rather than run the graph with a piece missing. If your module will be hosted that way, put the Lua in 📜 Scripts instead.

Exercise: secrets across the game

  1. Build Recipe 2 on one map, but remove its set_hud.

  2. After count, add a call: to game, name secret_found, value 1. In ◇ Graphs, the map's row now says calls secret_found, and a warning says nothing answers it.

  3. Press + new graph for the game, name it progress, and add a variable total starting at 0.

  4. Add an on_call named secret_found. The warning goes away, and the game's row says answers secret_found.

  5. Link it to an add_var total, with value linked from the on_call's value. Then a set_hud secrets, with value linked from a get_var total.

  6. Try adding an open_door to the progress graph. It isn't in its menu. That is the game graph telling you to call a level instead.

The game's graph runs call with to: level, after an every node, with nothing linked to entity. What happens?

  • Every level's graphs answer
  • The level the first player is in answers
  • Nothing: a call to a level needs an entity to say which, so it is skipped and logged

An every run has no entity. Link a player in, for example from a variable or a when_player_arrives chain.

A module has monsters. How many graphs can one of its maps hold?

  • 8: the runtimes take 6 slots, the module's and the map's Lua take 2
  • 16
  • As many as you like

A map has 16 script slots. Monsters, triggers and graphs need two slots each, plus one for the module's Lua and one for the map's own.

Where should "the player has the blue keycard, across every map" live, if a graph keeps it?

  • In each map's graph, with once
  • In a game graph's variable, set through a call
  • In a save_vars store

A game graph's variables are kept from level to level and saved with the game. A store would outlive a new game, which a keycard should not.
