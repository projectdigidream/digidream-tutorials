Thinking in graphs

A graph does nothing until something happens. Then it walks: from one node to the next along the white links, fetching values along the green ones. Once you can predict that walk, you can build anything in this track.

You'll learnwhat starts a run, how a run moves from node to node, when values are worked out, which order things happen in, how fields and data pins share a job, what each flow node does, and when a trigger is the better tool Time30 minutes Needsthe tour of the graph window in Graphs; it helps to know Triggers

This track goes deeper than the Graphs page in the Studio track. That page shows you the window: the board, the node menu, the side panel. This one is about what happens when the graph runs. Every node name links to its entry in Every graph node, which lists its pins and fields.

Try it first

The lab below has a small board, a palette of real node types, and a toy world with three imps, a switch and a door. It starts with the preset kill 3 to open the door already wired. The buttons under the picture fire events, and each run lights the nodes as it reaches them.

  1. Press ☠ a monster dies. Read the log. The start node dies starts a run, count adds 1 to kills, and if asks enough, which asks kills. The answer is false, and nothing is linked to if's false, so the run ends.

  2. Press it twice more. On the third death the compare is true, once lets the run through, and the door opens.

  3. Press reset the world, then drag a new link from kills's value pin to door's sector pin. The lab refuses nothing here: a number can be a sector. Kill three imps again. The door does not open, because door now opens sector 3, the value of kills. Tap that link to delete it.

  4. Try to link dies's entity pin into if's in pin. The lab says Exec links to exec, data to data. This is the one link the studio refuses as you draw.

  5. Load the toggle switch preset and press ✋ player presses use on the switch a few times. Watch door_open in the variables box flip each time.

A run starts at a start node

Every run begins at a start node. It has no white input, only a white output, usually called then. The node menu lists the start nodes first, in the group when …. They fire once for the moment they name, not on every tick that the state holds: when a player comes into a sector, not for every tick they stand in it.

The menu also offers every tick, and each trigger event by name in the trigger words group (when interact, when cross …). These are the event node. Its data outputs are what the event carried: entity, target, side, sector, crush_kind, ui_id, widget_id, value. An output the event did not carry is nil.

Most start nodes have filters: sector or tag, prop, kind, who. Read their defaults. who is players unless you change it. when_dies watches monsters by default, and when_hurt watches anyone.

Two kinds of link

  • Exec links (white, square pins) say what runs next. An exec output leads to one place only; a new link from it replaces the old one. An exec input can take many links, so several paths can join at one node.
  • Data links (green, round pins) carry a value. A data output can feed any number of inputs. A data input takes one link; a new one replaces the old.

You cannot link exec to data. You can draw an exec loop (a later node linking back to an earlier one), but data links may not form a cycle: the studio says the data links form a cycle through …, and the engine refuses the graph.

How a run moves

From the start node's exit, the run follows the exec link to the next node and does it:

  • An action (open_door, set_var, a trigger action) does its job and continues from then.
  • A condition (a trigger condition, or branch) continues from true or false.
  • A flow node does what it says: see The flow nodes.

When an exit has nothing linked to it, that path ends. Nothing is an error about that: an unlinked false is how you say "otherwise, do nothing".

A run is bounded. It may take 256 node steps. Past that, it stops, and the server log says a run went past 256 steps at node '…' and was stopped -- a loop? So an exec loop drawn by mistake cannot freeze the game.

Values are pulled, and remembered for the run

Nodes with no white pins at all, like get_var, compare, math, logic, random or health_of, are pure. Nothing runs them. A node that needs one of their values pulls it at the moment it runs, and the pure node works the value out then.

Each pure node is worked out once per run, and the run keeps the answer. That is why two readers of one random see the same number. It also has a sharp edge:

If a run reads get_var kills, then adds 1 to kills, then reads the same get_var kills node again, the second read gives the old value. The run remembered it. Use a second get_var node for the read after the change. A new run (a new event, or the far side of a delay) starts with nothing remembered.

Outputs of exec nodes are different. A spawn's entity output is whatever it last made in this run, read fresh each time.

The order things happen in

  • Within a run, everything happens in the same game tick, in link order, until a delay or a done exit pushes the rest later.
  • Several start nodes for one event all run, one after another: graphs in the order they were loaded, and inside a graph, in the order the nodes are in the file. The studio keeps them in the order you added them. Don't let two of them depend on which goes first; join them into one chain instead.
  • A sequence runs exit 0's whole chain first, then exit 1's, and so on, all in the same tick.
  • Changes to the world land at the end of the tick. A teleport moves its entity at the tick's flush point, so a position_of later in the same run still reads the old place.

Fields and data pins

A node has fields, which you type or pick in the side panel: a door's sector, a delay's ticks, a sound's name. Many fields also have a data pin of the same name. When a link goes into that pin, the link wins and the field says ← node.pin. With nothing linked, the field's own value is used.

  • A required field fed by a link needs no typed value.
  • Optional fields stay off the node until they have a value or a link. + N more… brings them on.
  • A numeric field with a data pin has a small 𝑥. Tap it to take the number from a variable instead. The studio writes that as a hidden get_var linked into the pin, so it is the same thing as drawing the link.
  • A trigger condition or action on the board has a data pin for each of its arguments of a type the engine can pass: whole numbers, fixed-point numbers, text, true/false, choices, sectors, and plain values.

The entity pin

Most "do to a thing" nodes have an entity input. Left unlinked, it means the event's own entity: the player who pressed use, the monster that died. Linked, it means whatever the link gives. If the link gives nothing (a spawn that could not spawn), the node does nothing. It never falls back to the event's entity, so a failed spawn feeding a kill cannot kill the player who set it off.

when_level_starts, every and after runs have no entity. A play_sound or set_hud left unlinked in such a run reaches nobody. The cutscene and camera nodes are the exception: in a run with no player, they act on every player in the level.

Some actions have a second exit for later:

  • fade, subtitle and camera_flythrough continue from then at once, and from done when they finish. That is how a cutscene is chained.
  • save_vars has failed, and load_vars has none.
  • when_near starts from near or away.

Loops

There is no loop node. To repeat, use one of these:

  • every N seconds, for a steady beat.
  • A delay whose then links back to an earlier node. Each pass is a new run, so it never hits the step limit. Guard it with a branch on a variable, so you can stop it.
  • A sequence, when you need a fixed handful of the same thing (spawn three imps).

Pending delays are not saved. A save keeps state, not what was in the middle of happening. A timer loop that was waiting when the game was saved does not resume after a load. If it must keep going, restart it from when_level_starts.

Triggers or graphs?

A graph's events, conditions and actions are the trigger vocabulary's, run by the same code. A door opened by either is the same door. So the choice is about how you want to write it:

Use a trigger for the classic one-liners: a door, a lift, a switch, a teleport. The presets write them in one tap. Use a graph when the logic has a shape: it counts, it waits halfway, it chooses, it talks to the game's graph, it drives a cutscene or a panel. The two live side by side on one map without trouble.

A branch's cond is linked to get_var lives, and lives is 0. Which exit does it take?

  • false, because 0 is false
  • neither: the run stops
  • true, because only false and nil count as false

A branch takes true for anything but false and nil, so 0 is true. Put a compare (lives <= 0) between them.

One run reads get_var kills (it is 2), then add_var kills 1, then reads the same get_var kills node again. What does the second read give?

  • 2: a pure node is worked out once per run
  • 3: it reads the variable again
  • nil: the variable changed

The run remembers each pure node's value. Use a second get_var node for the read after the change.

An every node fires a play_sound with nothing linked to its entity. What do players hear?

  • The sound, from every player
  • Nothing: an every run has no entity, so the sound has nobody to come from
  • The sound, from the map's centre

Unlinked, entity is the event's entity, and timer runs have none. Start from a node that has a player, or link an entity in.
